GAPS — the ONLY schema changes to make, as one migration file schema_gaps.sql:

sql-- 1. Prospect Cue needs a workflow status; nothing in the schema tracks it.
ALTER TABLE prospects
  ADD COLUMN status VARCHAR(50) NOT NULL DEFAULT 'new' AFTER rating;

Field-mapping notes controllers must implement (schema name ↔ frontend field name)


applications: frontend sends date_applied → store in applied_at column.
When returning a row, alias applied_at back to date_applied in the JSON so the
existing frontend code doesn't need to change.
prospects: frontend's Prospect Cue reads/writes status directly — now a real
column after the gap fix. No other mapping needed; company, title, url,
description, source, rating already match.
documents: frontend sends content (raw text) in the POST body. The controller
does NOT store this in a content column — there isn't one. Instead:
FileStorage::write() saves the text to
/documents/{document_type}s/{slugified-title}-{id}.txt, and the row stores that
path in file_path. company and job_title from the form go into metadata
(JSON: {"company":"...","job_title":"..."}). type from the form → document_type
column, name → title. On GET, the controller reads the file back and returns it
as content in the response so the frontend's editor still works unmodified.
tailored-resumes endpoint → resumes table: name → title, content →
content. target_role, company, keywords → metadata JSON.
cover-letters: company + — + title → title column (so it's readable
in a plain list), generated_text → content. hiring_manager, tone, jd_text,
company_detail → metadata JSON.
saved_searches: frontend's url field → query column.
settings: single row, id = 1. Flat columns (name, email, phone,
linkedin, portfolio, salary, arrangement, target_location, bio,
master_resume) map directly to frontend field names once you strip the set-
prefix (e.g. set-salary → salary). The category/key/value columns are
NOT used this phase — reserved, ignore them.
